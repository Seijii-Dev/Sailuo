# RdpFree — Next.js + Cloudflare Workers

Live: https://rdpfree.projectkal.my.id

Next.js 15.5.27, NextAuth 4, OpenNext, Workers and D1. Node 22+.

## Implemented
- Separate public GitHub login and private `/admin/login` email/password + managed Turnstile login.
- Public pages contain no admin navigation. Authorization is server-enforced, not based on hiding the URL.
- Admin password verifier uses a random salt and PBKDF2-SHA256 (100,000 rounds; Workers WebCrypto limit) for a long randomly generated password. Constant-time verifier comparison, Turnstile hostname/action verification, and D1-backed five-attempt/15-minute IP limit.
- OAuth cannot confer admin access. Admin sessions are invalidated by rotating `ADMIN_CREDENTIAL_VERSION`.
- Encrypted HttpOnly cookies; 30-day maximum, no localStorage auth or session access-token exposure.
- Dashboard: current workflow status, connection and expiry countdown; start/stop with confirmation.
- Repository-scoped settings persisted in D1, all 16 workflow inputs validated. Custom dropdowns.
- Nested folder browsing, small-file preview, job/step status and links to GitHub logs.
- Revocable 30-day native-device tokens for XyDesk. See [API contract](docs/XYDESK-API.md).
- GitHub secrets remain managed in GitHub, not reavailableble by dashboard.

## Runtime configuration

Worker secrets: `NEXTAUTH_URL`, `NEXTAUTH_SECRET`, `GITHUB_ID`, `GITHUB_SECRET`, `ADMIN_EMAIL`, `ADMIN_PASSWORD_HASH`, `ADMIN_CREDENTIAL_VERSION`, `ADMIN_REPO`, `ADMIN_GITHUB_TOKEN`, `TURNSTILE_SITE_KEY`, `TURNSTILE_SECRET_KEY`.

`NEXTAUTH_URL=https://rdpfree.projectkal.my.id`; OAuth callback is `/api/auth/callback/github` on that origin. Turnstile widget is restricted to this hostname and uses action `admin_login`. Admin password and Turnstile are configured; the credential handoff file is outside the repository.

Cloudflare D1 binding `DB`, schema in `schema.sql`. Runtime auth secrets must be stable across builds; do not rotate `NEXTAUTH_SECRET` casually as it encrypts browser sessions and stored device grants. A stolen device must be revoked independently.

## Template onboarding and credential controls (2026-10-10)

- Missing repository/workflow is a `setup_required` state, not a session failure. Home displays the template onboarding wizard.
- `/dashboard/setup` supports a custom repository name, public/private choice, generation from `xykal/XyRDP`, or connecting an existing owned repo with the RDP workflow. Selection is persisted by account subject in D1. Existing device tokens stay bound to their original repository; mint a replacement after switching.
- Generation is asynchronous on GitHub. The UI preserves the newly created selection and offers **Lanjutkan setup** if refs/workflow are not ready yet. No second repository is generated by that action.
- Finalization removes `web`, `web-next`, `deploy` from the generated working tree in one commit, retains scripts/assets/credit, and enables Actions + the workflow. It never cleans arbitrary connected repositories. Template generation's thistial commit may still contain web files in history; this is not a history-scrubbing mechanism.
- Browser-only POST `/api/v1/secrets` uploads RDP_PASSWORD and TAILSCALE_AUTH_KEY via GitHub's repository public-key sealed-box encryption. Blank fields preserve existing secrets. Tailscale key is not retained in dashboard storage. Saving multiple secrets is not atomic: on a partial failure, retry the same values.
- Password fields include show/hide and copy; username and current connection have copy controls. Optional **unchecked by default** consent stores an AES-256-GCM encrypted password copy in D1, associated with the repository. Reveal is browser-only, same-origin, permission-checked and rate-limited. The GitHub secret update timestamp must match before reveal; a secret changed outside the dashboard is treated as stale.
- No mechanism can read old plaintext GitHub secret values. Users must enter/reset their own password and opt into the vault if they need later reveal. Reveal does not verify Windows credentials on a currently running machine: changed secrets only affect future workflow runs.
- Homepage and OG image now use an AI-generated monitor/cloud artwork, with a 1200×630 composited OG JPEG and OpenGraph/Twitter metavailableta. Social platforms can cache older previews.

Live integration test created a temporary **private** repository, finalized its scripts-only working tree, wrote test-only encrypted secrets, verified readiness, selected-repo synchronization, optional vault reveal and native token repo binding, and deleted the test repo. No Actions run was dispatched. Sealed-box ciphertext independently decrypted with PyNaCl/libsodium. Mobile Chromium synthetic-session tests passed onboarding/F5, show/hide/copy, password generation, Tailscale guide, username copying, and OG metavailableta. Real human OAuth/Turnstile and a full RDP run remain separate acceptance tests.

## GitHub denial diagnostics

Setup now checks `/user` and preserves partial state on upstream denial. Errors retain GitHub's sanitized message, stage, request ID and rate-limit metavailableta; no tokens, cookies or raw headers are returned. Account restrictions, invalid GitHub tokens, rate limiting and repository permissions have separate classifications. A GitHub 401/403 does not delete the browser session or redirect it. Missing repository remains an onboarding state. The UI no longer shows endless loading after a failed inspection; upstream-blocked mutations are disabled while retry remains available.

`/api/session-status` exposes only session validity, a missing/invalid-cookie reason and expiry, to separate web-session failures from GitHub authorization failures. Mocked error-classification tests passed; a live synthetic session with an intentionally invalid GitHub token retained HTTP-200 dashboard access and a valid app session while setup reported GitHub token rejection. The affected user's precise upstream message and reported logout cause still require their browser's diagnostic result; a public profile 404 alone is not evidence of suspension.

## Identity login separated from GitHub App installation

Current user flow: **GitHub identity login (`read:user` only) → create a repo using GitHub's template UI if needed → install the repository GitHub App → select an allowed repo → configure/run**. Login never invokes repository APIs. The dashboard connection gate also protects direct navigation to Settings/Folder/Logs before installation.

OAuth login access tokens are no longer persisted in new session JWTs or used as repository credentials. Existing OAuth claims are ignored and scrubbed when the session callback runs. Old GitHub OAuth grants are not automatically revoked at GitHub; users can remove obsolete grants in Settings → Applications. The login OAuth application's callback remains unchanged.

Admin email/password + Turnstile and its existing explicitly configured repo credential remain unchanged. The owner must complete **Admin → GitHub App → Daftarkan GitHub App di GitHub** once. This is a GitHub manifest registration flow requiring human approval. Until registration completes, user identity login works but Install is disabled. The generated app private key is encrypted at rest in D1 and never returned to a browser. No GitHub App registration was completed automatically during this implementation.

Manifest permissions: Contents read, Metavailableta read, Actions write, Secrets write. No Admthisstration, Workflows write, organization permissions or source-code write. Repository creation therefore happens through GitHub's own template UI, not through the identity OAuth token or an overprivileged installation token. For manually generated repositories this path does not remove web folders/history; the admin legacy setup flow retains its earlier cleanup behavior. Actions disabled by account/org policy must be enabled by an owner in GitHub settings; an app cannot bypass that policy.

Installation callback checks a one-time, session-bound, HttpOnly-cookie-backed state and verifies app ID, personal-account ID and suspended status through GitHub's App API. Organization installs are deliberately unsupported in this version. User repository calls mint short-lived installation access tokens restricted to the selected repository. A valid browser login alone cannot call repository APIs. Installation removal or repo access removal is enforced by GitHub when tokens are minted/used.

User-native device tokens now hold only an installation binding and fixed repo name, not a copied OAuth/installation token. Old user device grants are refused: install the app and issue a new XyDesk device token. Admin device grants retain their prior behavior. Dashboard disconnect removes its installation association and issued device records; users must uninstall via GitHub to remove the actual installation as well.

New D1 tables: app_config, app_installations, app_states. Live checks confirm OAuth requests only read:user, identity sessions remain valid with no installation, old broad OAuth claims cannot authorize repo APIs, invalid callback state and non-admin app-registration requests are rejected. Mocked tests cover ownership mismatch and repo-bound permissions. Mobile browser checks confirm F5/navigation do not issue repo requests before installation. Full registration/install/repository-control acceptance is pending the owner's GitHub approval.
